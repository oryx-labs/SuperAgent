## 这一节在整门课里要完成什么

第一周要交出能指导实现的设计，第四节结束时接口、状态和验收标准都得定下来。第 02 节会把"做一个 SuperAgent"收窄成一份第一版产品定义，这件事有个前提：学员得先判断出一个持续工作的 Agent 系统，比自己现在手上的 Coding Agent 多了哪几层工程能力，并且选好一条最想亲手验证的链路。第 01 节就做这件事。

学员进来的时候，大多已经用 Codex 或 Claude Code 做完过真实的开发任务，也会写 Web 服务、数据库、调度和部署。他们常见的困惑是：资料里 Router、Worker、Agent OS、事件驱动、Watchdog 这些词都见过，但分不清哪些是模型和 Coding Agent 自己会解决的，哪些得由系统来承担；也看不出自己已有的后端经验能接到哪一层。

这节课的主线是：模型和 Coding Agent 会越来越强，但"一个任务怎样做完"和"企业员工怎样持续把工作交给 Agent"是两个问题。第二个问题需要一个掌管身份、任务、环境、权限、成本、审计和交付的工作系统，这部分正好是有经验的后端工程师能接手的。课程结束时，学员手里应该有一张自己的能力地图，地图上标出了一条要在后面三周验证的链路。

课程类型是概念与判断课，不写代码。

## 讲解推进

### 1. 从一次熟悉的成功开始，再加上公司里的条件

开场就用学员已经做到的事：在本地让 Claude Code 完成一个需求，改代码、跑测试、交结果。接着把同一件事放进一家知识付费公司（课程贯穿案例）：需求是产品经理在网页上提的，提完会关掉页面；同一时间另一个人也在提需求；Agent 要读公司仓库、碰到凭据；跑了四十分钟进程挂了；最后得有人验收，公司还得知道这次花了多少钱。

这些条件一加，问题就出来了，可以收成八个：任务从哪里来、由谁执行、执行时能访问什么、并发任务怎样隔离、失败后怎样恢复、花了多少、谁来验收、结果怎样留在企业。这八个问题是本节后半段画地图要用的坐标，讲的时候先抛出来，不急着回答。

### 2. 三类系统各自解决什么问题

按"解决谁的什么问题"给现有系统分类，不做功能评测：

| 类型 | 主要解决的问题 | 课程里提到的参照 |
|---|---|---|
| 个人助手 | 一个人跨渠道、长时间地和 Agent 打交道，有连续的上下文 | OpenClaw、Hermes Agent【具体口径待确认，见文末】 |
| 长任务执行器 | 一个任务在一个环境里持续跑完，包括工具调用、代码修改和验证 | Codex、Claude Code 等原生 Coding Agent；Agent OS 类思路【指向待确认】 |
| 企业工作平台 | 很多员工把工作交给 Agent，组织掌握身份、权限、成本、审计和交付 | 本课要做的 SuperAgent |

这张表要讲出的判断：前两类各自把一部分问题做得很好，第三类不是把前两类拼起来，而是多出一层"组织对工作的掌控"。讲师在这里要说清楚：个人 AI 工具有价值，企业平台要做的是把工作组织起来、留存下来，不是替代它们。

### 3. 读 DeepSeek 的 Super-agent 设计探索：目标怎样逼出架构

重点读《Super-agent 设计探索：迈向更自主的 Agent 系统》提出的四个目标：连续、高效、主动、持久。讲法是从目标倒推机制，让学员看到架构是被需求逼出来的：

- 要保持跨信道的连续交互，同时又能并行做事，于是有了 Router 和 Worker 的分工：Router 维护连续交互，Worker 隔离并行执行具体任务；
- 要主动，Agent 就得能被事件触发，但大部分事件不需要它行动，所以要做事件过滤；
- 要持久，就得有异步调用、状态与环境分离和 Watchdog，任务才能活过一次请求、一次进程退出。

【目标和机制的对应关系是依据课程大纲转述的，备课时要对照原文核对，尤其是"高效"具体对应哪项机制。】

这一段必须讲清边界：原文明确说这是架构探索，公开原型也不是正式产品；课程借的是它提出的问题和设计方法，做的是我们自己的企业版 SuperAgent，不声称复刻 DeepSeek 内部系统，也没有获得官方授权。

### 4. 企业场景还要多出哪几层

DeepSeek 的文章回答了"Agent 怎样更自主"。企业平台还得回答"组织怎样掌控 Agent 做的工作"。把第 1 段的八个问题拿回来，逐个放进课程的四层职责里，这张表同时就是四周的路线图：

| 问题 | 由哪一层负责 | 在哪一周落地 |
|---|---|---|
| 任务从哪里来 | 入口：员工对话、定时触发、外部事件 | 第三周 Chat / Automation，第四周 IM / Webhook |
| 由谁执行 | Router 做语义判断和分派；控制面执行选择策略 | 第二周 07，第四周 14 |
| 执行时能访问什么 | 控制面的权限策略 + Worker 的受控环境 | 第二周 08，第四周 15 |
| 并发任务怎样隔离 | Worker 的独立工作区 | 第二周 08 |
| 失败后怎样恢复 | 控制面的 Task / Attempt 状态 + Watchdog | 第二周 06，第三周 11 |
| 花了多少 | 用量归因到 Task、用户、项目 | 第二周 07 |
| 谁来验收 | 控制面的审批与人工验收 | 第三周 11，第四周 16 |
| 结果怎样留在企业 | 控制面保存 Event、Artifact 和审计 | 第三周 09–11 |

讲这张表时有一个承重判断要讲透：Router 可以用模型做判断，但任务状态、权限、审批和费用这类确定性的事实必须由控制面持有，不能只存在 Router 的模型 Session 里。第 04 节画架构时会正式展开，这里只是先埋下。

### 5. 你已有的能力接在哪里

把学员已有的工程能力放上同一张图。Web 服务、数据库、并发、调度、日志、部署，基本都落在入口和控制面；新增的能力集中在 Agent 这一侧：Session、Context、工具调用、沙箱与工作区、结果验证，以及模型的不确定性给状态管理带来的新麻烦（例如"结果未知"这种状态）。

这一段要让学员从"我会调用模型、会用 Coding Agent"走到"我能判断一个 Agent 系统缺哪一层工程能力"。也要说清本课的完成程度：16 节课要做的是一条能跑、能解释、能检查的最小主链路；大规模分布式调度、MicroVM 池、完整多租户和生产级高可用会进入架构讨论，但不在一期交付范围内。

### 6. 收束：带着一条链路进入第 02 节

收在一个判断上：看一个 Agent 系统，先看它把哪些事实交给了确定性的系统、哪些判断交给了模型，再看它缺哪一层。接着交代下一节要用到本节什么：学员选好的那条链路，会在第 02 节被收窄成第一版产品定义和验收用例。

## 作业

交一张"已会能力 / 新增能力"地图，再选一条最想亲手验证的链路。

地图以第 4 段的八个问题为纵轴，每一行写三件事：你在过去的项目里怎样解决过类似问题（举一个具体项目，没有就写没有）；放到 Agent 系统里，哪部分经验还能用、哪部分不够；你目前判断它属于哪一层。

选链路时，从主链路"请求进入 → 创建 Task → 分派 Worker → 调用一种真实 Coding Agent → 持续返回事件 → 保存结果与用量 → 人工验收"里挑一段，用三五句话说清：为什么选这段，你预计最难的地方在哪，第几周、用什么现象就能证明它跑通了。

最后写一个你还拿不准的问题，第 02–04 节会回头处理。

评价看两点：归层的理由是否站得住，选的链路能不能给出可以观察的验收现象。不看图画得漂不漂亮、写得多不多。这份作业会直接进入第 02 节产品定义的输入。
