# 技术架构

::: info 目标架构
本页介绍 SuperAgent 架构的目标形态。当前版本仍是控制面和 Agent CLI 跑在同一台服务器上;隔离的沙箱、多台机器上的 Worker、模型网关正在建设中(见[路线图](./roadmap))。
:::

SuperAgent 不重造 Agent,而是直接驱动官方的 Agent CLI(Claude Code、Codex、Qwen Code、Kimi 等),自己专注公司层面的事:谁来做、在哪里跑、用哪个模型、花了多少、成果归到哪里。Agent 会执行它自己生成的任意命令,所以按不可信对待,架构上把「决定做什么」和「在哪里做」分开。

## 三层架构

| 层 | 信任 | 负责 | 绝不持有 |
| --- | --- | --- | --- |
| **控制面** | 可信 | 界面和接口、全部业务逻辑、多租户与权限、调度、模型网关、MCP 工具服务、数据和文件存储 | — |
| **Worker**(每台机器一个) | 半可信 | 启停沙箱并限制资源、转发输出、准备工作区、上报心跳 | 数据库凭证、模型 Key、刷新令牌 |
| **沙箱**(每个员工一个) | 不可信 | 运行 Agent CLI 和 Agent 的命令,保存员工的工作区 | 以上全部 |

![SuperAgent 分层架构](/diagrams/architecture-layers-zh.jpg)

- **一个控制面服务所有公司。** 所有公司的数据在同一个库里,用公司字段区分。
- **运行时插件化。** microVM、gVisor、Docker 都可以用来运行沙箱。每个插件声明自己的隔离等级,调度据此决定不同公司能否混放在同一台机器上。
- **控制面调度,Worker 执行。** 只有控制面能同时看到所有机器的容量、每家公司的配额,以及每个员工的沙箱在哪台机器上。

## 部署与通信

运行时只允许 5 条通信:控制面不直连沙箱,沙箱访问不到 Worker 和数据库。

![多机部署,以及允许的 5 条通信](/diagrams/architecture-deployment-zh.jpg)

1. **Worker → 控制面**:Worker 主动连上控制面并保持连接,运行指令从这里下发,输出从这里回传。Worker 不开放入站端口。
2. **沙箱 → 控制面**:只能访问 MCP 工具服务和模型网关,凭单次运行令牌,令牌绑定这家公司、这个员工和这次运行。
3. **沙箱 → 出口代理 → 外网**:出口代理拦截内网、控制面和云主机元数据地址,其余按策略放行。
4. **控制面 ↔ 飞书 / 钉钉**:消息长连接和文档接口都由控制面处理,员工的令牌不进沙箱。
5. **模型网关 → 模型上游**:厂商 API,或客户自己的模型网关。

## 模型网关

所有模型调用都经过控制面里的模型网关,这让 SuperAgent 对模型厂商保持中立:

- **以透传为主。** 网关换上真正的 Key、按模型路由、从返回结果里读取 token 用量。工具调用、思考过程、提示缓存都原样保留。
- **三种协议覆盖各家厂商**:Anthropic Messages、OpenAI Chat Completions、OpenAI Responses。调度会选一个能说上游协议的 CLI。
- **客户自己的模型网关是一等上游。** 模型列表和价格由客户自己提供,员工对应的 Key 和请求头可以往下传,客户网关原有的统计照样能用。

## 一套代码

| 部署方式 | 是什么样子 |
| --- | --- |
| **单机** | 控制面、Worker 和沙箱都在一台机器上,用 docker compose 拉起。三层的边界不变,以后扩容不用改架构。 |
| **多机** | 控制面至少两个实例,共用 MySQL 和对象存储;每台机器跑一个 Worker。 |
| **SaaS 与私有化** | 同一套源码。私有化就是只有一家公司,可以用 Docker 运行时;SaaS 里多家公司混跑,用 microVM 或 gVisor。 |

完整的技术文档(模块、关键设计、数据流转)在代码仓库的 `docs/prd/superagent-architecture.html`。
