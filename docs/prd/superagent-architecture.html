1概述

SuperAgent 是给公司用的 AI 协作工作系统：公司里每个人都和 AI 一起干活，干出来的东西沉淀为公司的资产。它的核心价值按优先级排序是：沉淀资产、协作交接、方法复用、成本路由、审计与治理。

系统的特殊之处在于：Agent 底层是 Claude Code、Codex 这类命令行工具（下称 CLI），它们会在自己所在的机器上执行任意命令、读写文件。所以这套架构的核心问题是：如何让很多家公司、很多员工共用一套系统，同时让每个 Agent 只能碰到它该碰的东西。

1.1 设计目标

一套代码，两种形态SaaS 和私有化部署是同一个系统；私有化只是只有一家公司。
Agent 按不可信对待Agent 跑在隔离的沙箱里，看不到数据库、密钥和别人的东西。
凭证不出控制面模型 Key、OAuth 刷新令牌、数据库凭证只存在控制面。
运行时插件化microVM、gVisor、Docker 都是插件；调度根据隔离等级决定能否混放。
单机到多机不改架构三层边界从第一天就在，扩容只是加机器。
兼容客户已有的设施客户自己的模型网关、内网 GitLab、SSO 都能直接接入。

1.2 术语

术语含义
公司租户。数据、设置、集成、模型 Key、配额、账单都归属某家公司。私有化部署只有一家公司。
员工公司里的用户。Agent 总是代表某个员工干活，用这个员工的权限和授权。
Agent / SuperAgentAgent 是员工创建的 AI 同事；SuperAgent 是每个员工专属的负责人 Agent，负责拆解任务、分发给其他 Agent。
运行CLI 的一次执行：对话里的一轮回复，或任务里的一个阶段。是调度和计量的基本单位。
控制面服务所有公司的那部分系统：界面、接口、业务逻辑、调度、模型网关、数据库。完全可信。
运行面执行 Agent 的机器集合，每台机器上有一个 Worker、一个出口代理和若干沙箱。
Worker每台运行面机器上的常驻程序，按控制面的指令启停沙箱、转发输出。半可信。
沙箱每个员工一个的隔离运行环境，里面跑 CLI 和员工的工作区。不可信。
运行时插件沙箱的实现方式：microVM、gVisor、Docker、本机进程（仅开发用），各自声明隔离等级。
模型网关控制面里所有模型调用的必经之路，负责换上真正的 Key、路由、计量、限速。
单次运行令牌每次运行发给沙箱的临时凭证，只对这家公司、这个员工、这次运行有效，运行结束即失效。
连接Agent 可用的外部工具（GitHub、GitLab、Notion、飞书文档等），员工用自己的账号授权。

2整体架构

SuperAgent 采用三层架构：控制面、Worker、运行时沙箱。后两层合起来叫运行面。这样分的根本原因是，Agent 会执行它自己生成的任意命令，必须当作不可信的代码对待。所以系统把「决定做什么」和「在哪里做」分开：业务决策、数据和凭证都留在控制面；Agent 的执行放到隔离的沙箱里；中间由 Worker 负责把控制面的指令落到具体机器上。

2.1 三层的分工

第一层控制面可信

系统里唯一可信的部分：所有业务决策、数据和凭证都在这里。

负责
界面和接口、全部业务逻辑、多租户与权限、调度、模型网关、MCP 工具服务、数据库和文件存储
部署
逻辑上只有一个，服务所有公司；物理上是多个无状态实例，共用 MySQL 和对象存储
约束
不运行任何 Agent 代码，也不直接连到沙箱
第二层Worker半可信

每台运行机器上的执行器，把控制面的决定落到这台机器上。

负责
按指令创建和回收沙箱、限制资源、转发输出流、准备工作区、上报心跳和剩余容量
部署
每台机器一个独立的小程序，启动后主动连回控制面，不开放入站端口
约束
不做调度决策；不持有数据库凭证、模型 Key 和刷新令牌
第三层运行时沙箱不可信

Agent 真正干活的地方，每个员工一个隔离的环境。

负责
运行 CLI，执行 Agent 的命令，保存员工的工作区和会话状态
部署
由运行时插件创建：microVM、gVisor 或 Docker
约束
没有长期凭证；只能访问控制面的 MCP 和模型网关；出网只经出口代理

三层之外是外部系统：模型厂商（或客户自己的模型网关），以及飞书、钉钉、GitHub、GitLab 这类办公和研发系统。控制面直接对接模型和办公系统；沙箱访问外网时只经出口代理。

控制面存储保存全部数据MySQL（一个库，所有公司共用）；ClickHouse（可选，用于用量分析）；对象存储（文件、工作区快照，按公司分前缀）；主密钥（KMS 或本地密钥文件）。

运行时运行时插件沙箱的具体实现microVM、gVisor、Docker、本机进程（仅开发用）。每个插件声明隔离等级，调度据此决定能否混放不同公司。
运行时沙箱员工专属的隔离运行环境预装全部 CLI（Claude Code、Codex、Qwen Code、Kimi、DeepSeek、GLM）和本地 MCP；挂载员工的工作区；空闲回收，用到再拉起。
外部
—模型上游提供模型能力厂商 API、客户自有的模型网关、私有部署的模型；只经控制面的模型网关访问。
—办公与研发系统Agent 用来读写外部系统的对象飞书 / Lark、钉钉、Notion、GitHub、Gitee、GitLab、Jira / Confluence，员工用自己的账号授权。

2.4 为什么这样分

安全执行任意命令的部分和数据、凭证物理隔开。沙箱就算被攻破，也拿不到数据库、模型 Key 和别人的东西。
扩展加机器只扩运行面；控制面只做决策和存储，不跑重活。
多租户调度根据运行时的隔离等级决定能否让不同公司混放，同一批机器可以服务多家公司。
一套代码单机部署时，三层放在同一台机器上，边界不变；SaaS 和私有化只是部署规模不同。

4关键设计

4.1 多租户

一个控制面、一个库，所有公司的数据放在一起，用公司字段区分。每张业务表都有公司字段，唯一键里也包含公司字段（例如「同一家公司内用户名唯一」）。

  • 公司上下文：接入层根据子域名或公司代码识别公司，之后整个请求都带着公司上下文；后台任务、单次运行令牌、Worker 回传的事件也都带着公司。
  • 在存储层统一加条件：公司条件由存储基类自动拼接，业务代码不需要手写，也不能绕过；不带公司上下文的查询直接报错。MySQL 没有行级安全，所以这道防线只能放在代码里，必须用测试守住。
  • 全局表很少：只有公司列表、平台管理员、Worker 节点这类跨公司数据不带公司字段。
  • 归属到公司的配置：系统设置、集成（每家公司有自己的飞书应用）、模型服务商和 Key、连接、技能、自动化。
  • 公平：后台任务（消息分拣、任务调度、自动化）按公司轮流处理；每家公司有任务并发和模型用量的配额。
  • 加密：每家公司有自己的数据密钥，由主密钥加密保存（信封加密）。
  • 私有化：就是只有一家公司的同一个系统，安装时创建这家公司。

4.2 身份与权限

  • 三种角色：平台超管（运营 SaaS 的人）、公司管理员（客户的 IT）、员工。私有化部署时，前两者是同一批人。
  • 登录：先识别公司，再按这家公司的方式登录：自有账号、SSO 或 LDAP。
  • Agent 的身份：Agent 总是代表「发起这次运行的员工」，用他的权限和他的连接授权。多人协作的 Agent 也一样：谁发起，就在谁的沙箱里、用谁的身份跑。

4.3 执行与隔离

  • 每个员工一个沙箱：常驻，空闲回收，下次用到时再拉起。员工的对话和任务都在自己的沙箱里跑，CLI 的会话状态和工作区也挂在这里。
  • 一次运行：控制面组装运行参数（用哪个 CLI、模型、提示词、MCP 配置、单次运行令牌），通过调度交给某台 Worker；Worker 在员工沙箱里执行 CLI，把输出逐行转回控制面。
  • 沙箱里没有任何长期凭证：模型调用经模型网关，由网关加上 Key；工具调用回到控制面的 MCP 服务；外网经出口代理。
  • 工具白名单不变：沿用现在按运行类型（对话、任务、SuperAgent）区分的工具授权，只是令牌改为绑定公司。

4.4 调度

放到哪台机器由控制面统一决定，因为只有控制面能同时看到所有机器的容量、每家公司的配额，以及每个员工上次在哪台机器。Worker 只负责执行。决策依次考虑：

  1. 隔离等级：Docker 节点只放同一家公司；microVM、gVisor 节点可以混放。
  2. 公司配额：超过并发上限的运行排队等待。
  3. 员工亲和：优先放回这个员工沙箱所在的机器，工作区和会话状态都在那里。
  4. 容量：按内存和 CPU 的余量选机器。

机器失联时，上面正在进行的运行标为失败，可以重试；员工的沙箱在别的机器上用最近一次工作区快照重建。

4.5 运行时插件 草案

Worker 通过统一的插件接口管理沙箱。每个插件声明自己的隔离等级，调度据此决定能否混放：

interface SandboxRuntime {
    IsolationLevel isolation();        // STRONG：microVM、gVisor · SHARED_KERNEL：Docker · NONE：本机进程（仅开发）
    Sandbox ensure(SandboxSpec spec);  // 按员工创建或复用：镜像、资源上限、工作区卷、网络（只通出口代理）
    Execution exec(Sandbox s, Command cmd, Map<String, String> env);  // 输出逐行流式返回，支持取消
    void stop(Sandbox s);              // 空闲回收
    Snapshot snapshot(Sandbox s);      // 工作区快照，用于迁移和故障恢复
}

4.6 模型网关

  • 以透传为主：CLI 发来什么协议，就原样转给上游。网关只做三件事：换上真正的 Key、按模型名路由、从返回结果（包括流式输出）里读出 token 用量。工具调用、思考过程、提示缓存等特性都原样保留。
  • 只需支持三种协议：Anthropic Messages（Claude Code）、OpenAI Chat Completions（大部分国产模型和客户网关）、OpenAI Responses（Codex）。厂商之间的差别主要是地址、认证方式和模型名，靠配置处理。
  • 用 CLI 去配合上游：调度在选 CLI 时看上游支持什么协议，以此避免协议转换。只有「上游只支持 OpenAI 协议，又一定要用 Claude Code」时才需要转换，那时优先用成熟的开源组件，不自己写。
  • 客户网关是一等上游：模型列表从客户网关读取；价格由客户自己填；员工和任务的标识可以放进请求头传给客户网关，方便它按人统计；客户按人发 Key 时，支持员工到 Key 的映射。
  • 统一治理：按公司和员工限速；多 Key 轮换、失败切换、成本路由都集中在网关；token 用量在这里统一计量，比从各家 CLI 输出里换算更准。

4.7 网络与出网

  • 沙箱放在不能直接出网的网络里，只能连到本机的出口代理；CLI、npm、git 都按 HTTPS_PROXY 走代理。
  • 始终拦截：内网网段、控制面、数据库端口、云主机元数据地址 169.254.169.254。
  • 两种策略：默认放行公网；严格模式只放行白名单（模型 API、已配置连接的地址、代码仓库、软件源镜像）。
  • 管理员配置的内网系统（例如内网 GitLab）自动加入放行名单，也可以手工添加例外。

4.9 存储与文件

  • MySQL：一个库，所有公司共用，存全部业务数据（用户、公司、Agent、任务、对话、文件索引、连接、Key、设置），只有 MySQL 一种实现：这些数据要事务和唯一约束。
  • 分析数据默认也在 MySQL：token 用量、Agent 运行日志、耗时记录。量大以后可以设 superagent.storage.analytics=clickhouse，只把这几张只增不改的表放到 ClickHouse，其他数据不受影响（2026-11-10 起，取消了「整个系统切到 ClickHouse」的做法）。
  • 对象存储（本地盘或 S3 兼容）存文件和工作区快照，按公司分前缀。现在「文件」已支持两种；对话附件、头像、Logo、技能图片还只在本地盘（按公司分目录），工作区快照未做。
  • 主密钥：本地密钥文件或环境变量；每家公司一把数据密钥，由主密钥加密后存在公司表里。KMS 以后按需接在主密钥这一层。
  • 工作区在 Worker 本机，每个员工一个独立的卷。不用共享目录（NFS）：那样每台 Worker 都能看到所有人的工作区，一台被攻破影响太大。
  • 文件进出只走协议：附件、file_get 由控制面经 Worker 送进沙箱；Agent 的产出由 Worker 取回、存进对象存储，再登记到「文件」。控制面不再直接读写工作区路径。

4.10 控制面高可用

控制面是所有公司共用的，至少要两个实例。现在有几类状态在进程内存里，需要逐一移出：

进程内的状态现在在哪目标做法
运行中的输出流对话服务里的进行中轮次、SSE 连接输出事件经事件总线分发，浏览器连到哪个实例都能收到
后台循环记忆整理、自动化、收件分拣、SuperAgent 后台、任务看门狗、文件打标签等用数据库租约选出一个实例执行，或按公司分片
飞书 / 钉钉长连接每个应用一条，在进程内每家公司的应用由一个实例持有（租约），实例挂了由别的实例接管
任务会话池任务服务内存会话状态在沙箱里，控制面只保存引用
Worker 长连接（新增）Worker 连到任一实例，实例间通过事件总线转发指令

事件总线选什么（数据库轮询、Redis 或消息队列）是待定事项。可以分两步走：先「一主一备」，再做多个实例同时工作。

5数据流转

5.1 一轮对话

控制面和沙箱之间只有两条通道：经 Worker 的运行通道，和沙箱回调的 MCP、模型网关通道。

5.2 任务执行

  1. 创建：员工在对话里提出、Agent 自己开、SuperAgent 分发，或者自动化触发。创建时只记录任务和类型（编码或普通）。
  2. 选模型：执行前，按难度选出最便宜但够用的模型，并记录理由；失败时逐级升档。
  3. 排队与调度：进入公司的任务队列，按配额放行；调度把每个阶段的运行放到员工沙箱所在的机器上。
  4. 执行：编码任务按 PRD、开发、验收三个阶段跑；普通任务直接执行。需要确认时暂停，员工在任务页或待办里一键确认。
  5. 产出：产出文件经 Worker 取回，存进对象存储并自动归档到「文件」；结果回到发起任务的那个对话，并生成待办或通知。

5.3 外部消息（飞书 / 钉钉）

  1. 接收：每家公司的飞书或钉钉应用，由控制面的一个实例保持长连接。消息按发送人匹配到已关联的员工；群消息分给群里每一位已关联的员工。
  2. 分拣：立刻入库，并标上轻重：P0 紧急、P1 重要、P2 一般。接收和处理分开进行，模型处理慢也不会丢消息。
  3. 处理：P0 立刻交给员工的 SuperAgent 后台，P1 每小时一批，P2 进每日简报。外部消息原文只当数据，里面的指令不会被执行。
  4. 结果：需要员工做的生成待办；需要马上知道的发提醒；适合团队做的提计划等确认。所有消息都能在待办页的「消息」标签里看到。

5.4 文件

  1. 进：员工上传附件或给出链接，文件先存进对象存储并登记到「文件」；运行开始时，控制面经 Worker 把需要的文件送进沙箱工作区的 uploads/。Agent 也可以用 file_get 按需拉取。
  2. 出：Agent 用 file_save 交付成果时，Worker 从沙箱取回文件，上传到对象存储，控制面登记并自动归档到对应目录。
  3. 可见范围：发起人和 Agent 的成员可见；SuperAgent 能管理员工能看到的全部文件。

5.5 连接授权

  1. 公司配置：公司管理员在「集成」里配置一次应用（GitHub、Gitee、飞书、Notion 等的 OAuth 应用）。
  2. 员工授权：员工在「连接」页用自己的账号授权，得到的令牌加密存在控制面。
  3. 运行时使用：本地 MCP（例如 GitHub、Notion）每次运行拿到一个短期访问令牌；飞书和钉钉文档由控制面代为调用，令牌不进沙箱。
  4. 到期续期：控制面用刷新令牌自动续期；续期失败时，提示员工重新授权。

6安全边界

每一层只持有完成本职必需的东西。运行时只允许 5 条通信，其余方向一律不通。

层信任负责持有绝不持有只能访问
控制面可信 接口、业务域、调度、模型网关、MCP 工具服务 数据库凭证、主密钥、模型 Key、员工的 OAuth 刷新令牌 — 数据库、对象存储、模型上游、飞书和钉钉；从不直连沙箱
Worker半可信 在本机启停沙箱并限制资源、转发输出流、准备工作区、上报心跳 自己的节点凭证（可以随时吊销） 数据库凭证、模型 Key、刷新令牌 控制面（主动长连接）、本机的运行时

7部署形态

单机

控制面、Worker 和沙箱都在一台机器上，用 docker compose 拉起。三层的边界不变，以后扩成多台机器不用改架构。宿主机需要安装 Docker。

多机

控制面至少两个实例，共用 MySQL 和对象存储。每台物理机跑一个 Worker，用 --server 和节点令牌连到控制面。

SaaS 与私有化

同一套源码。差异只在五处：公司数量、运行时插件、模型上游、登录方式、权益开关。私有化离线安装用预先打好的镜像。

升级：每个版本附带表结构变更脚本，并写明从哪个版本升到哪个版本、按什么顺序执行，运维按正常流程操作。开发环境保留「本机进程」运行时，spring-boot:run 的开发体验不变，但它不隔离，不能用于生产。

9演进路线

从现在开始，新写的代码就按目标架构来：数据带公司归属，不再新增全局设置；控制面不再新增直接读写工作区的代码。这样不打断现在的迭代，也不会继续积累要返工的代码。存量改造分四步，每一步都能单独上线：

第二步拆成两段（2026-11-10 讨论）：先在现在的单进程里把运行时隔离做出来，再把执行拆到 Worker。2a 不碰文件进出，靠目录挂载让现有代码照常工作，所以改动集中、能尽早上线隔离；2a 先切出的执行接口，就是 2b 要变成网络协议的那一层，不会白做。代价是 2a 期间控制面仍直接读写挂载的工作区，必须防住沙箱里的符号链接把控制面引到工作区之外。

  1. 第一步
    数据层多租户公司表和公司上下文；所有表加公司字段，存储层统一加条件；登录时识别公司；两级管理员；设置、集成、Key、连接归公司。
  2. 第二步 a
    运行时插件和沙箱（仍在控制面进程里）先在控制面里切出执行接口：控制面只组装一次运行（CLI、模型、提示词、MCP 配置、单次运行令牌、工作区），交给执行后端；第一个后端就是现在的本机进程，行为不变。再在它下面接运行时插件：本机进程（开发用）和 Docker（可选 gVisor）。每个员工一个沙箱，镜像预装全部 CLI；工作区先以目录挂载进沙箱，控制面现有的读写工作区代码不用改；沙箱只能连出口代理和控制面的 MCP 入口。上线后不同公司在进程、文件、网络上彼此隔离。详见 运行时插件与沙箱。
  3. 第二步 b
    控制面与 Worker 分离把 2a 的执行接口变成协议：Worker 主动长连接控制面，按指令启停沙箱、转发输出、上报心跳和容量；文件进出改走协议，控制面不再直接读写工作区路径；单机部署用 compose 同时拉起控制面和一个 Worker。模型网关在这一步或紧随其后上线，Key 撤出沙箱。私有化和多机部署从这一步开始可用。
  4. 第三步
    microVM 和调度器Firecracker / Kata 插件；按隔离等级、配额、亲和、容量调度；工作区快照与故障迁移。之后不同公司可以混跑在同一台机器上。
  5. 第四步
    控制面高可用事件总线；后台循环和 IM 长连接改用租约；先一主一备，再做多实例同时工作。
