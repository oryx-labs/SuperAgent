1目标与边界

目标：现在所有公司、所有员工的 CLI 都直接跑在控制面所在的机器上，用同一个系统用户、同一个 HOME，能看到彼此的工作区、CLI 会话文件，能连数据库和内网。这一步让每个员工的 Agent 跑在自己的沙箱里：进程、文件、网络都和别人隔开。第一个落地目标是 117 能跑。

做什么：在控制面里切出「启动进程」这一层接口；运行时插件化（本机进程、Docker、gVisor、microVM，以后 Kubernetes）；每个员工一个沙箱；出口代理；资源上限和回收；把控制面自己起的 CLI 调用也搬进沙箱。

不做什么（留给第二步 b）：Worker 独立进程和长连接协议；文件进出走协议；模型网关。这一步沙箱和控制面仍在同一台机器上，工作区以目录挂载进沙箱，控制面现有读写工作区的代码不用改。

2已定决策

事项决定
运行时Docker、gVisor、microVM 都做成插件，部署方自己选；接口按以后能接 Kubernetes 来设计。117 用 gVisor。
模型 Key模型网关上线前（第二步 b），Key 仍以环境变量进沙箱。每家公司只用自己的 Key，公司之间不串；同公司的 Agent 读得到本公司的 Key，接受。
CLI 版本CLI 预装在沙箱镜像里，由平台统一发布。用沙箱运行时的时候，公司管理员不能安装、升级 CLI；本机进程运行时保留现在的安装功能（开发用）。
沙箱归谁先按工作区的主人：对话跑在 Agent 所有者的沙箱里（协作 Agent 的其他成员发起的一轮也是）；任务跑在任务发起人的沙箱里，子任务跟主任务一样。
资源由本方案定（见第 7 节）。
默认开关上线时默认仍是本机进程，配置打开才用沙箱；开发环境始终用本机进程。

4总体设计

4.1 一条接缝：启动进程

现在各个 CLI 运行器（Claude、Codex、Kimi、Qwen、DeepSeek、GLM）都是自己拼好命令行和环境变量，然后 new ProcessBuilder(...).start()，再逐行读输出。拼命令是各 CLI 自己的事，不用动；要换掉的只有最后「在哪儿启动这个进程」。所以接缝切在这里：

// core：运行器只依赖它，不知道进程跑在本机还是沙箱里
interface ProcessLauncher {
    LaunchedProcess launch(LaunchSpec spec);
}
record LaunchSpec(Owner owner,                 // 公司 + 员工：决定用谁的沙箱
                  List<String> argv, Map<String, String> env,
                  Path workdir,                // 控制面看到的工作区路径
                  List<Path> files) {}       // 运行要读的临时文件（MCP 配置、settings）
interface LaunchedProcess {                    // 和 java.lang.Process 一样用
    OutputStream stdin(); InputStream stdout(); InputStream stderr();
    int waitFor(Duration timeout); void destroy();
}

第一个实现 LocalLauncher 就是现在的做法，行为不变；第二个 SandboxLauncher 找到这个员工的沙箱，把路径换成沙箱里的路径，交给运行时插件执行。第二步 b 再加一个 WorkerLauncher，把同样的启动、输入输出、取消搬到长连接上。这条接缝就是将来 Worker 协议里的「执行」那一半，不会白做。

4.2 沙箱管理

SandboxManager（新模块 superagent-sandbox，L1，只依赖 core）负责：按员工找到或拉起沙箱、记最后使用时间、空闲回收、容量控制、服务重启后按标签认领已有的沙箱。插件只负责「怎么起一个沙箱、怎么在里面执行命令」。

项设计
标识每个（公司，员工）一个沙箱，名字 sa-<公司>-<员工 id 前 12 位>，带标签 superagent.company、superagent.user、superagent.image。
镜像复用 docker/Dockerfile 里已有的 cli-base 阶段（node 24 + Claude Code、Codex、Qwen、Kimi、DeepSeek 等，装在 /opt/cli，非 root 用户 uid 10001），加上 git、python、uv，以及常用 MCP 包的缓存（GitHub、Notion、钉钉、mcp-atlassian），避免每次 npx 现下载。版本随产品发布。
挂载宿主机 <data>/sandboxes/<公司>/<员工>/work 挂到 /work：这个员工所有的对话工作区、任务工作区、上传文件、技能安装目录都在这下面。.../home 挂到 /home/agent：CLI 的会话文件（续聊靠它）、配置都在这里，每人一份。别的什么都不挂，尤其不挂 Docker socket。
路径换算控制面继续用宿主机路径；SandboxLauncher 把工作目录、命令行和环境变量里出现的宿主机路径换成 /work/...。运行器写的临时文件（MCP 配置、settings、DeepSeek/Qwen 的配置）改写到这个员工的工作区下，不再写系统临时目录。
执行每次运行在已起的沙箱里执行一次命令（Docker 系是 docker exec -i 的等价 API 调用），标准输入输出原样接回控制面。常驻的 Claude Code 进程就是一个没结束的执行，随沙箱一起回收。
令牌和现在一样：每轮的 MCP 令牌、员工的连接令牌、本公司的模型 Key 以环境变量传给这一次执行，不写进镜像、不留在沙箱的文件里。

4.3 选哪个运行时

运行时是部署级配置（属于平台，不属于某家公司）：superagent.sandbox.runtime = local | docker | gvisor | kata | k8s，默认 local。启动时做一次自检：Docker 连得上、runsc 或 kata 已注册、需要 KVM 的有 /dev/kvm、镜像拉得到；不满足就报出具体原因并拒绝启动沙箱，不偷偷退回本机进程。自检结果显示在管理后台。

混放规则：插件声明隔离等级。共享内核的 docker（runc）默认只允许一家公司用这台机器（私有化场景）；机器上已经有第二家公司时拒绝为它起沙箱，并提示换成 gVisor 或 microVM。可以用 superagent.sandbox.allow-shared-kernel-multi-company=true 显式放开。

5运行时插件

// core：每个插件实现它；SandboxManager 只认这个接口
interface SandboxRuntime {
    String name();                         // local / docker / gvisor / kata / k8s
    IsolationLevel isolation();            // NONE · SHARED_KERNEL · STRONG
    Readiness check();                     // 自检：依赖是否就绪，不就绪的原因
    Sandbox ensure(SandboxSpec spec);      // 镜像、资源上限、挂载、网络；已存在则复用、停了就启动
    LaunchedProcess exec(Sandbox s, List<String> argv, Map<String, String> env, String workdir);
    void stop(Sandbox s);                  // 空闲回收：停掉，保留挂载的数据
    void remove(Sandbox s);                // 员工离开公司、公司删除时
    List<Sandbox> adopt();               // 服务重启后认领按标签找到的沙箱
}
插件隔离等级宿主机要求117实现要点
localNONE无可用（开发）就是现在的本机进程；只给开发和单人试用，不隔离。
dockerSHARED_KERNELDocker 20+、cgroup v2可用容器 + 资源限制 + 只读根文件系统 + 去掉全部 capability + no-new-privileges + 非 root。通过 Docker Engine API（Unix socket）操作，不调命令行。
gvisorSTRONGDocker + runsc 注册为运行时；不需要 KVM可用（装 runsc 后）和 docker 插件是同一份代码，只是建容器时指定 runtime=runsc；没有 KVM 时 gVisor 用 systrap 模式。
kata（microVM）STRONGDocker 或 containerd + Kata；需要 /dev/kvm不可用同样复用 docker 插件，runtime=kata；Kata 底下可选 Firecracker、Cloud Hypervisor 或 QEMU。不单独对接 Firecracker：那样要自己管 rootfs、网络和执行通道，工作量大得多。
k8s（以后）由 RuntimeClass 决定Kubernetes 集群—一个沙箱 = 一个 Pod，RuntimeClass 选 gvisor 或 kata；执行走 Pod exec；工作区用卷。只在第二步 b 之后有意义（那时文件进出已经不靠本机目录），本步只保证接口不挡路。

docker、gvisor、kata 三个插件都是「OCI 镜像 + 在容器里执行命令」，共用一个实现和同一个镜像，差别只在运行时名和隔离等级。所以「都开发」的成本主要在 docker 这一个；后两个是参数加自检加测试。

6网络与出网

项设计
沙箱网络每家公司一个 Docker 内部网络（internal，没有到外网的路由）；同公司的沙箱在一起，不同公司不通。
出口代理沙箱唯一能连的地址。本步先放在控制面进程里，单独监听一个端口（HTTP 代理，支持 CONNECT），只接受来自沙箱网络的连接；第二步 b 随 Worker 一起搬出去。沙箱里设好 HTTP_PROXY / HTTPS_PROXY，CLI、npm、git、pip 都走它。
拦截规则先解析域名，按解析出的 IP 判断，每次重定向、每次连接都重新判断（防 DNS 重绑定）：始终拦截回环、私有网段、链路本地（含 169.254.169.254 元数据）、IPv6 本地和唯一本地地址、控制面自己的其他端口、数据库端口。管理员在「连接」里配置的内网地址自动放行。只放行 HTTP/HTTPS，git 走 HTTPS，不支持 SSH。这套判断和 superagent-00 正在做的「读公开链接」防内网访问用同一份代码。
上游代理放行的请求再交给宿主机已有的出网方式；117 上就是 Clash（127.0.0.1:7890）。
控制面入口沙箱访问控制面的 MCP 服务也经过代理，代理只放行 MCP 路径，并要求带单次运行令牌。模型网关上线后再加一条。
记录每次拦截记一条（公司、员工、目标地址、原因），在运行日志里能看到，方便排查「Agent 为什么连不上」。

7资源与回收

项默认值理由
单个沙箱2 核、2 GB 内存（不给 swap）、512 个进程、文件句柄 4096一个 Claude Code 进程加它起的 MCP、npm、构建命令，常见 0.5–1.5 GB；2 GB 留了余量，跑飞了也只杀它自己。
工作区磁盘每人 5 GB 软上限overlay 和普通 ext4 没有通用的目录配额，先定时统计、超了在后台提示并拒绝新运行，以后再换真正的配额。
单机容量同时运行的沙箱数 = (总内存 − 预留) ÷ 单个沙箱内存；预留默认 4 GB预留给控制面 JVM、MySQL 和系统。117：(15 − 4) ÷ 2 ≈ 5 个。
空闲回收15 分钟没有执行就停掉（数据保留）常驻 Claude Code 进程 10 分钟空闲退出，沙箱再晚一点停；停掉的沙箱下次用到时再启动，Docker 系 1–2 秒。
满了怎么办先停掉最久没用的空闲沙箱；没有空闲的就排队任务本来就排队；对话最多等 60 秒，还没位置就报「运行环境忙，请稍后再试」。每家公司还受现有配额（同时运行的任务数）限制。
删除员工被移出公司、公司被删除时删沙箱和数据目录避免残留别人的工作区。

这些都做成配置项（属于部署，不属于某家公司），117 先用默认值，跑一段看实际占用再调。

8要搬进沙箱的调用

凡是会执行 CLI 或第三方命令的地方，都改用 ProcessLauncher。不属于任何员工的调用，跑在这家公司的「系统沙箱」里（员工 id 固定为 system，不挂任何员工的工作区）。

调用现在在哪改为在谁的沙箱

任务、复杂任务的子任务、编码流程同上，经 TaskService任务发起人

记忆整理、文件自动打标签、任务选模型、任务打标签AgentMemoryService、FileTagger、ModelCall相关员工；没有员工的走系统沙箱

9控制面直读工作区的防护

这一步控制面还会直接读写挂载出来的工作区：送附件、file_get 取文件、file_save 存产出、安装技能、写 output.md。沙箱里的 Agent 能在工作区里放任何东西，所以控制面要按「目录内容不可信」来处理：

  • 符号链接：读之前解析真实路径，必须仍在这个员工的工作区之内，否则拒绝；写的时候不跟随链接（打开时带 NOFOLLOW），目标已存在且是链接就拒绝。防止 Agent 建一个指向 /etc 或别人目录的链接，借控制面的手越界。
  • 特殊文件：只处理普通文件和目录，跳过设备文件、命名管道、套接字。
  • 大小：file_save 等读入前先看大小，超过上限拒绝，防止拿一个巨大文件拖垮控制面。
  • 属主：沙箱里是 uid 10001；控制面写进工作区的文件要能被它读写（目录统一属于 10001，控制面写完设属主或组权限），避免 Agent 读不到附件。

第二步 b 改为文件走协议后，这些检查移到 Worker 里，控制面不再碰工作区路径。

10实施步骤

每步都能单独合并、单独上线；前三步不改变任何运行行为。

  1. S1
    切出启动进程的接缝core 加 ProcessLauncher；第 8 节列的所有起进程的地方改用它；LocalLauncher 保持现状；临时文件改写到工作区下。验收：全量测试通过，本机行为不变。
  2. S2
    沙箱管理与本机插件新模块 superagent-sandbox：SandboxRuntime 接口、SandboxManager（按员工找或起、空闲回收、容量、认领）、路径换算、local 插件、配置开关与自检。验收：开关打开、用 local 插件跑通对话和任务。
  3. S3
    沙箱镜像在 docker/Dockerfile 里加 sandbox 阶段（基于 cli-base），预装工具和 MCP 包缓存；发布流水线一起出镜像。验收：镜像里各 CLI --version 都能跑，非 root。
  4. S4
    Docker 和 gVisor 插件通过 Docker Engine API 建容器、加资源限制和安全选项、执行命令、回收、按标签认领；gVisor 只是换运行时名。验收：两家公司同时对话，各自在自己的容器里，互相看不到工作区和进程。
  5. S5
    网络与出口代理每公司内部网络；控制面内的出口代理和拦截规则；MCP 入口经代理；拦截记录进运行日志。验收：沙箱里访问 MySQL 端口、169.254.169.254、内网地址都被拒，公网和模型 API 正常。
  6. S6
    其余调用搬进沙箱模型检测、Key 检测、模型列表、记忆整理、打标签、选模型、连接能力列表都走系统沙箱或员工沙箱；沙箱运行时下关闭 CLI 安装、CliConfigWriter 不写宿主机。验收：沙箱模式下控制面本机不再起任何 CLI 进程（进程审计）。
  7. S7
    工作区防护与隔离测试第 9 节的符号链接、特殊文件、大小、属主处理；第 11 节的隔离测试套件。验收：测试套件在 docker 和 gvisor 上都通过。
  8. S8
    上 117装 runsc 并注册到 Docker；拉镜像；配置 runtime=gvisor、容量 5；先只开给自己的组织跑一段，看内存、启动耗时、gVisor 兼容性。
  9. S9
    microVM（Kata）插件参数和自检，测试在有 KVM 的机器上跑。117 用不上，给私有化和以后的物理机节点准备。Kubernetes 插件放到第二步 b 之后。

11测试与验收

  • 同一套契约测试跑每个插件：起沙箱、执行、输入输出、取消、超时、回收后再起、服务重启后认领。没有 Docker 的机器自动跳过 docker 系插件的测试，CI 和 117 上必须跑。
  • 隔离测试（两家公司、各两个员工）：读不到别人的工作区和 HOME；看不到别人的进程；连不上数据库、控制面非 MCP 端口、元数据地址、私有网段；环境变量里没有别家公司的 Key；内存超限只杀自己的沙箱；符号链接越界被拒。
  • 回归：对话、续聊（换会话、常驻进程）、任务、复杂任务、编码流程、附件和 file_save、技能、连接（stdio 和 HTTP）、各家 CLI 的 token 计量，在 local 和 gvisor 下结果一致。
  • 性能：记录首次起沙箱、停后再起、每轮多出来的耗时，进现有的「耗时」分段（新增「准备运行环境」一段）。

12风险与待定

事项说明
gVisor 兼容性gVisor 自己实现了一套系统调用，绝大多数 node、python、git 没问题，个别工具可能不支持；文件读写和 npm 安装会比 runc 慢。S8 先在 117 上实测各家 CLI 和常用 MCP。
Docker socket 的权限控制面要操作 Docker，就等于拥有宿主机 root。控制面本来就是可信的，这一步接受；第二步 b 由 Worker 持有，控制面不再碰。
镜像体积与更新预装全部 CLI 和 MCP 缓存后镜像会有 1–2 GB；CLI 更新频繁，发布节奏要跟上，否则用户会觉得「版本老」。
CLI 分发条款把 Claude Code 等打进镜像对外分发，就是架构文档待定事项里「CLI 的使用条款」，这一步之后变成实际问题，要先核实。
续聊和常驻进程CLI 的会话文件从共用的 HOME 换到每人一份，现有会话在切换那一刻接不上：第一次进沙箱时按「换会话」处理（带记忆、最近对话和文件，见 Agent 记忆的新会话规则）。
