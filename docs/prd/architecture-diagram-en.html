SuperAgent Architecture

One control plane serves every company, with all their data in one database, separated by a company column. Agents run in isolated sandboxes, one per employee, spread across several physical machines. The runtime is a plugin: microVM, Docker and others can be plugged in. The control plane decides where work runs; a Worker on each machine carries it out. Model keys and other secrets never leave the control plane. SaaS and on-premises deployments run the same code; on-premises is simply a system with one company.

Layers

Multi-machine deployment and traffic

Only these five kinds of traffic are allowed at run time: the control plane never connects to a sandbox directly, and a sandbox can reach neither its Worker nor the database.

Trust boundaries

Each layer holds only what its job needs.

Control planeTrusted Interfaces, domains, scheduling, model gateway, MCP tool service Database credentials, master key, model keys, employees' OAuth refresh tokens — Database, object storage, model upstreams, Feishu and DingTalk; never a sandbox directly
WorkerSemi-trusted Starts and stops sandboxes on its machine with resource limits, relays output, prepares workspaces, reports heartbeats Its own machine credential (revocable at any time) Database credentials, model keys, refresh tokens The control plane (outbound connection), the local runtime
SandboxUntrusted Runs the CLI and the agent's commands A per-run token, the employee's own short-lived connector tokens, the employee's workspace Everything above, and the Docker socket The control plane's MCP and model gateway; the internet only through the egress proxy

One codebase, three ways to deploy

One machine

Control plane, Worker and sandboxes on one machine, started with docker compose. The three layers keep their boundaries, so growing to more machines needs no change to the architecture.

Many machines

At least two control-plane instances sharing MySQL and object storage. Each machine runs one Worker, and the scheduler decides which machine each run goes to.

SaaS and on-premises

The same source code. On-premises is one company and can use the Docker runtime; SaaS mixes companies on shared machines and uses microVM or gVisor.
